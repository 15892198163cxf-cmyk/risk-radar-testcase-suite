# QA 雷达增强用例生成器

## 安装路径与 OCR 配置

以当前加载的 `SKILL.md` 所在目录的绝对路径作为 `SKILL_DIR`，执行前替换命令中的 `${SKILL_DIR}`（PowerShell 可使用 `$env:SKILL_DIR`）；业务输入、输出仍使用用户工作区路径。PDF 解析依赖 `paddleocr-doc-parsing`，凭据使用 `PADDLEOCR_API_TOKEN`。可用 `PADDLEOCR_SKILL_DIR` 指定其安装根目录；未指定时依次查找同级技能目录和本套件上层 `common/` 中的技能目录。图片 OCR 需先定位已安装的 `paddleocr-text-recognition/SKILL.md`，将其所在目录作为 `OCR_SKILL_DIR`；依赖未安装时提示补齐。

This is the isolated generator used by `risk-radar-testcase-workflow`. Do not
route ordinary no-radar testcase requests here. The standalone
`qa-testcase-generator` remains the compatibility path for those requests.

## ⛔ 强制门控：第一轮回复禁止生成用例

**无论需求多么清晰、完整、明确，第一轮回复绝对不能开始写用例。**

第一轮回复只允许做以下事情（且必须按当前输入状态完成）：
1. 问用户选择生成模式（标准 / 详细）
2. 如果需求载体尚未到达，只确认模式和输入类型，然后等待文件/正文
3. 如果需求载体已经到达，先完成解析；只做简短接收确认，不在未分析前硬问业务问题

### 三道门控必须独立判断

1. **模式门控**：用户必须明确选择标准/详细。用户说「走详细模式」只表示模式已选定。
2. **需求载体门控**：必须等需求正文、PDF、Markdown、图片等实际到达并完成解析。用户说「需求文档一会儿发」「稍后发 PDF」时，只能确认已记录模式并等待文件。
3. **分析确认门控**：需求载体解析后，必须完成 Step 2/3/4 的结构化分析、知识库命中、交叉分析，再输出澄清问题并等待用户回答；如果没有澄清问题，也必须请用户确认理解正确。用户回答/确认前不得进入 Step 6 生成。

**禁止误判：**
- 「走详细模式」≠「不用问了」
- 「用 qa-testcase-generator-radar 技能走流程」≠「跳过澄清」
- 「需求文档一会儿发，是 PDF」≠「需求已确认」
- 「帮我写用例」≠「直接生成最终用例」
- 用户只回复「标准」或「详细」只关闭模式门控，不等于确认需求理解、不等于回答澄清问题。
- `NO_REPLY`、超时、沉默、用户未回复，都不能视为默认确认。
- 澄清问题必须来自 Step 4 交叉分析结果；未完成需求结构化和知识库交叉时不要为了凑门控而提出空泛问题。

**需求载体尚未到达时的固定回复：**
> 收到，已记录使用{标准/详细}模式。请发送需求文档/PDF；收到后我会先解析，完成结构化分析、知识库命中和交叉分析，再输出澄清问题；等你回答或确认后再开始生成用例。

**判断标准：** 如果你的回复里出现了「用例标题」「测试步骤」「预期结果」「TC-」「scene:」等用例内容，说明你违反了门控规则。立刻停下来，删掉用例部分，改为提问。

**为什么：** 用户给的需求往往有隐含假设、未说明的边界、未确认的业务规则。跳过确认直接写 → 写出来的用例方向错误 → 返工成本远大于多问一轮。

**唯一例外不是跳过分析：** 用户提前说"不用问了直接写"/"不需要确认"/"按我说的直接生成"/"无需澄清，直接生成"，只能记录为偏好，不能取消 Step 2/3/4。只有在需求载体已经提供并解析完成、Step 4 交叉分析已经输出后，用户明确接受 Step 4 列出的默认假设，或用户在看到 Step 4 问题后再次明确要求按默认假设生成，才可以不再等待逐题回答。否则必须等用户回答/确认。

## 生成模式（开始前必问用户）

### 模式一：标准模式 🟢
适用：需求明确、功能简单、时间紧迫。预期 **30-80 条**。
- 同一规则的不同输入值**合并为1条**
- 边界值、异常值**按类型合并**
- 联动场景**按模块粗测**（每个关联模块 1-3 条）
- 安全测试**按类型合并**
- 前后端校验**只测一端**

### 模式二：详细模式 🔴
适用：核心业务、复杂逻辑、需要严格覆盖。预期 **80-200+ 条**。
- 每个输入值**独立成条**
- 边界值/异常值**逐个独立**
- 联动场景**逐 scene 覆盖**
- **前后端校验分开测** + **接口级测试**
- **状态流转全覆盖**（操作×状态矩阵每格都写）
- **文案/提示语逐条验证**
- 权限、版本、状态记忆、字段作用域等问题会影响预期时，必须先确认再生成。
- ⚠️ 选择详细模式后，必须加载 `references/detailed_mode_rules.md` 获取完整要求

### 什么时候选哪个

| 情况 | 推荐模式 |
|------|----------|
| 需求简单、时间紧、功能明确 | 🟢 标准 |
| 核心业务模块（下单、支付、权限） | 🔴 详细 |
| 新功能上线压力大 | 🟢 标准 |
| 复杂逻辑 + 多状态 + 需要严格覆盖 | 🔴 详细 |
| 快速冒烟/验收 | 🟢 标准 |
| 安全要求高 / 历史 bug 多的模块 | 🔴 详细 |

### 同一场景对比示例（向用户解释粒度差异时使用）

> 场景："名称"输入框，限制 1-50 字符

**标准模式 → 1 条用例：**
```
标题：名称输入边界值和异常值校验
步骤：分别输入空、1字符、50字符、51字符、特殊字符<script>
预期：空→提示必填；1字/50字→成功；51字→提示超限；特殊字符→转义或拦截
```

**详细模式 → 6 条用例：**
```
1. 名称为空提交 → 前端提示"请输入名称"
2. 名称恰好1字符 → 保存成功
3. 名称恰好50字符 → 保存成功
4. 名称51字符 → 前端提示"不超过50字符"
5. 名称含XSS脚本 → 前端转义展示
6. 绕过前端直接调接口传51字符 → 后端返回参数错误
```

## 核心流程

### 知识库根目录

默认知识库目录名为 `qa-knowledge/`，不要写死绝对路径。

解析顺序：
1. 用户显式提供的知识库路径。
2. 当前工作区下的 `qa-knowledge/`。
3. 当前 skill 目录同级的 `qa-knowledge/`。

不要再使用带 `-v2` 后缀的旧路径或旧能力名。

如果三处都不存在，将 `generator_kb_status` 记为 `not_configured`：
- 不得声称命中生成器本地规则、旧用例或缺陷库；
- 不阻断需求解析、雷达召回、澄清或基于需求生成用例；
- 不要把它表述成“雷达不可用”或“没有历史 Bug/历史用例”；雷达提供方的数据源与 `qa-knowledge/` 相互独立；
- 默认不要在首段播报内部目录检查。仅当它实质限制了结论，或用户询问数据源时，在证据边界中简短说明“生成器附加本地知识库未配置，不影响已执行的雷达召回”。

### Step 1: 接收与解析

支持输入格式：文字描述、Markdown、PDF、图片、或以上组合。

**PDF 解析**（强制 PaddleOCR 官方 Job API）：
```bash
python "${SKILL_DIR}/scripts/parse_pdf.py" --file-path "PDF路径"
python "${SKILL_DIR}/scripts/parse_pdf.py" --file-url "PDF URL"
```
- 底层走官方异步 Job API（`paddleocr.aistudio-app.com/api/v2/ocr/jobs`），稳定可靠
- 超过 100 页先用 `split_pdf.py` 分页处理

**⚠️ 强制全文读取（禁止只读前 N 字）：**
解析成功后，必须将 `result["text"]` 的全部内容分批读完，每批 ≤ 8000 字，直到读完为止。
- 禁止只读前几千字后跳过剩余内容
- 禁止用「摘要」代替全文阅读
- 读完后在内部记录实际总字符数，作为后续分析的依据
- **原因**：PRD 中操作按钮的状态条件、字段校验规则、异常提示文案等关键约束，往往分散在文档各处，局部阅读必然遗漏

**图片解析**（强制 PaddleOCR，不要用模型视觉能力直接看图）：
```bash
python "${OCR_SKILL_DIR}/scripts/ocr_caller.py" --file-path "图片路径"
python "${OCR_SKILL_DIR}/scripts/ocr_caller.py" --file-url "图片URL"
```

**接收/解析后处理（⛔ 此阶段禁止生成用例）：**
- 只确认已收到并完成解析，必要时简短复述 1-3 句话。
- 如果尚未选择模式，先问用户选择标准/详细。
- 如果已选择模式，可以进入 Step 2/3/4 做分析，但不得进入 Step 6 生成。
- 不要在未完成 Step 4 交叉分析前硬凑澄清问题；真正的澄清问题必须在 Step 4 输出。

如果用户只发起任务但需求载体尚未到达（例如「需求文档一会儿发」「稍后发 PDF」「PDF 等会儿给你」）：
- 只确认已记录的生成模式和输入类型
- 只请求用户发送需求载体
- 不得复述不存在的需求正文
- 不得开始 Step 2、Step 3、Step 4、Step 6 或生成用例
- 不得把该消息视为「无需澄清」或「直接生成」授权

PDF/图片解析完成后，即使用户已经提前选择详细模式或提前说过「不用问直接生成」，也必须先完成 Step 2/3/4；只有 Step 4 已输出且用户回答/确认后，才进入 Step 5/6。

### Step 2: 当前需求结构化分析

只基于当前需求文档/图片/OCR 内容做结构化，不引入历史知识结论。

输出检索锚点：
- 模块、页面、入口、角色/权限线索、客户端/版本/系统线索
- 字段、控件、按钮、列表列、筛选/搜索/排序/分页/空态线索
- 操作、状态、数据流、上下游/读取端/生效端线索
- 功能点 FP、约束条件、可验证文案、异常/边界/安全信号

Step 2 只为后续知识库检索确定方向，不生成用例，不输出最终澄清结论。

### Step 3: 知识库命中

用 Step 2 的检索锚点读取相关知识，避免全量硬读：
- `qa-knowledge/rule-index.yaml` → 命中规则 → 读取完整规则文件
- `qa-knowledge/testcase-library/index.yaml` → 命中旧用例/关联模块用例
- `qa-knowledge/defect-pool/online-bugs.yaml` → 命中 `online_bug`
- `qa-knowledge/testcase-library/*.yaml` → 命中 `history_bug: true`
- `qa-knowledge/defect-pool/matching-weights.yaml` → 缺陷打分权重
- `qa-knowledge/learned-patterns.yaml` 和 `.learnings/LEARNINGS.md`

缺陷分层：
- `bug_tier: online_bug`：来自 `defect-pool/online-bugs.yaml`，命中后强制高密度覆盖。
- `bug_tier: history_bug`：来自 testcase-library 中 `history_bug: true` 的历史失败/回归用例，命中后强制防回归覆盖。
- 兼容老数据：只有 `history_bug: true`、没有 `bug_tier` 的用例，一律按 `bug_tier: history_bug` 处理。

Step 3 输出「知识库命中摘要」：命中规则、旧用例、缺陷、关联模块、历史经验；仍不生成用例。

#### 可选：风险雷达结果

当上游 `risk-radar-testcase-workflow` 提供符合
[`radar-result.schema.json`](../risk-radar-testcase-workflow/schemas/radar-result.schema.json)
、并且由当前需求在本次任务中直接产出，或由用户明确提供且
`requirement_fingerprint` 与 `evidence_snapshot_id` 均匹配当前输入的
`radar_result` 时，才进入雷达辅助模式。不得复用其他需求、身份不明或
证据快照不匹配的历史结果。具体适配规则见
[`references/radar_integration.md`](references/radar_integration.md)：

- 消费 `risks[].test_points`，把它们作为已筛选的高价值测试提醒；不要把
  原始 Bug 再追加成第二份 `online_bug` / `history_bug` 列表。
- 用 `source_ids` 与本 Step 命中的缺陷去重；同一来源只保留一次，并合并适用范围与证据边界。
- 仍须完成本 Step 的规则库、旧用例、缺陷库和关联模块检查。雷达不能替代需求知识交叉分析。
- 仅 `applicable` 和 `no_direct_match` 可携带风险；`not_applicable` 不得向当前需求注入其他产品的历史证据。
- 交接中的问题不因出现在结构化文件中就视为已确认。确认状态必须来自上游工作流记录的用户回答或用户明确接受的默认假设。
- `generator_kb_status: not_configured` 只表示没有生成器附加知识库。只要雷达提供方可用，仍须完成雷达召回并按雷达实际结果报告命中，不能提前暗示“没有历史证据”。

没有合法 `radar_result` 时，完全按照原 Step 3 行为执行，不要求雷达
字段、不改变普通生成流程。如果用户明确请求了集成工作流但结果无效，
返回上游修复，不得静默丢弃风险后宣称完成雷达辅助生成。

### Step 4: 交叉分析与澄清门控

先做 A，再做 B，最后统一输出澄清问题。

**A. 当前需求/原型自身完整性检查**
- 检查当前需求中没说明但会影响预期结果、覆盖范围、测试数据、前置条件或步骤的点。
- 原型有控件但没说明交互、字段规则、异常态、回显、生效范围时，必须纳入分析。
- 同一句需求存在两个以上合理解释，必须纳入分析。
- 需求/原型自身未明确的内容也可以成为澄清问题来源，不必等知识库冲突才提问。
- 不把 PRD「待确认问题」章节当成 A 的全集。沿核心链路逐项检查：对象身份与权限、输入与归一化、状态与时效、配置变更对既有数据的影响、跨端/通知/日志读取，以及异常时是否改变安全边界。只记录真实影响当前用例的疑点，不为每个维度硬凑问题。
- HTML 内嵌图片也属于本轮需求证据。逐张核对其所处章节：有角色、端、状态、文案或数据规则的图片必须进入决策候选；仅展示布局的图片注明原因。即使 PRD 写着「不制作新原型」，也不能据此跳过已有界面参考。正文与图片范围不同，先判断是补充还是冲突，无法确定预期时提问。
- 新规则需要首次保存时间、最近操作时间、到期时间等字段时，检查上线前存量记录是否已有这些值及迁移口径；不能用「旧记录保留」代替期限或状态的接管规则。若接管方式改变预期且当前资料未定义，列为提问。

**B. 知识库交叉分析**
- 当前需求 vs 规则库：是否冲突、继承、废弃、局部适用。
- 当前需求 vs 旧用例：旧前置、预期、字段规则、权限范围是否仍适用。
- 当前需求 vs 缺陷库：history_bug/online_bug 是否命中，风险场景是否仍需覆盖。
- 当前需求 vs 关联模块：下游页面、接口、导出、筛选、权限、数据回显、统计、通知、埋点是否受影响。
- 当前需求 vs learned-patterns：历史教训是否适用。

**两项固化规则的影响判断：**在交叉分析阶段判断本次需求是否影响调用行为、既有数据及其读写。相关时读取 `references/request_and_data_checks.md`，将会改变预期的未知项并入现有澄清，将已确认的适用检查纳入现有 Step 5 生成策略，供 Step 6 编写用例。

只检查本次相关的动作、对象和链路，不遍历全部历史场景。不新增步骤、独立分析表、检索动作或确认轮次；规则内容已加载时直接复用。

如果处于雷达辅助模式，还必须执行 **C. 雷达结果合并**：

- 按“需要用户决定的产品规则 + 对用例的影响”合并雷达问题与 A/B 产生的问题，不能只按文字相似度去重。
- 同一问题保留 PRD、规则库、用例库、缺陷库、雷达等全部来源，只向用户询问一次。
- 上游已经展示且用户明确回答的问题可以复用答案，不得重复询问；如果当前分析发现实质不同的新问题，仍须返回本门控。
- 雷达没有提出的问题不能覆盖或取消 A/B 发现的需求疑点。
- 先完成 A/B 的独立候选清单，再看雷达的 `questions`。不得直接复制雷达的提问清单作为 Step 4 最终清单；两者数量相同本身不表示遗漏，但须能逐项解释 A/B 候选如何处理。

**雷达辅助模式的澄清完整性检查（生成前硬门槛）**：
- 在正常 Step 4 回复中，用一张精简表列出所有会改变用例预期、范围或数据的决策候选；每项标注来源/位置、影响和处理：`提问`、`当前需求已明确`、`仅执行数据待备`、`不适用`。后三者必须给出可核对的依据；“按现网”“按实现”不能用来掩盖需要产品决定的规则。
- 当前 PRD 明列但未关闭的问题必须出现在表中；旧版本/旧运行提出过的问题只用于发现候选，不能把旧答案当作本轮确认，也不能把旧问题原样全问一遍。若用户要求「当成第一次」，所有仍开放的产品决定都须本轮重新确认。
- `提问`项必须进入下方正式澄清问题表并有建议口径；`仅执行数据待备`只能用于不改变预期的样本、接口路径或环境数据，需指出用例待验条件。不能确定是否影响预期时按`提问`处理。
- 在用户回答后、进入 Step 5 前，对照候选表复核一遍：是否有未回答的`提问`，以及是否有被建议口径悄悄固定的其他规则。有则回到 Step 4，不得以速度目标、雷达校验通过或“全部按建议”跳过。
- 在展示问题前执行一次独立候选覆盖审查：先从本轮 PRD/原型与 Step 2 功能链路列候选，再核对知识库、雷达问题及可找到的旧运行问题清单；旧答案只能帮助发现候选，不自动关闭本轮问题。尤其核对对象/权限、输入与数据口径、状态与时效、配置变更、跨端通知/日志、异常安全边界。逐项标注 `提问`、`当前需求已明确`、`仅执行数据待备` 或 `不适用`；某个候选没有可核对的处置就不能发出最终问题表。此审查对当前需求做取舍，不按固定数量凑问。
- 用 [Step 4 校验说明](references/step4_gate.md) 构造临时审查输入。正文传完整 UTF-8 解析文本；HTML 需求还须传原始 `.html` 以核对内嵌图片清单：`python scripts/validate_step4_decisions.py <本轮PRD完整文本> <临时Step4审查JSON> --source-html <原始HTML>`。非 HTML 省略 `--source-html`。`[INVALID]` 时补齐候选、处置或问题后再展示；`[OK]` 仅证明候选到提问的结构闭环，仍须人工核对语义、来源和建议口径。临时 JSON 是校验输入，不是额外交付物，也不替代正常 Step 4 表格。

澄清问题要求：
1. 只问会影响用例设计的问题，最多 10 个。
2. 每个问题标明来源：`PRD/原型`、`规则库`、`用例库`、`缺陷库`、`关联模块`、`历史经验`。
3. 每个问题说明影响：预期结果、覆盖范围、测试数据、前置条件、优先级、是否生成某类用例。
4. 不要机械套用固定问题模板；只问本次交叉分析真实发现的问题。
5. 用户未回答、`NO_REPLY`、只选择模式，都不得进入 Step 6。
6. 如果问题来自旧规则/旧用例/缺陷库与当前需求的冲突，必须把冲突点说清楚，不能只问泛泛的权限、版本、字段问题。
7. 每个问题必须给出一条明确、可执行的“建议口径”，并说明建议依据。建议口径是待用户确认的默认方案，不得伪装成 PRD 已明确事实；确实无法安全建议时，明确写“无安全默认值”并说明阻断原因。

输出格式：
```markdown
## 交叉分析结果
| 来源 | 命中内容 | 与当前需求关系 | 是否需要确认 |
|---|---|---|---|

## 决策候选处理（雷达辅助模式）
| 来源及位置 | 会影响什么 | 处理 | 当前依据或不提问原因 |
|---|---|---|---|

## 澄清问题（必须回答后再生成）
| 编号 | 来源 | 问题 | 建议口径（默认方案） | 建议依据 | 为什么必须确认 | 影响范围 |
|---|---|---|---|---|---|---|
```

如果没有澄清问题：
- 输出「澄清问题：无」。
- 说明已检查：需求/原型、规则库、用例库、缺陷库、关联模块、历史经验。
- 请求用户确认「理解正确，可以开始生成」；用户确认前不得进入 Step 6。

只有满足以下任一条件，才可以继续：
- 用户回答了全部澄清问题。
- 用户在看到澄清问题后明确说「按默认假设生成/无需确认直接生成」。
- 澄清问题为无，且用户确认「理解正确，可以开始生成」。

雷达辅助模式下，“用户回答了全部澄清问题”指合并后的问题全集均已回答。模式选择、沉默或只确认雷达内容，不能替代对新增 PRD 疑点的确认。

### Step 5: 生成策略确认

根据 Step 4 的用户回答、用户明确接受的默认假设，或 Step 4「澄清问题：无」后的用户确认，输出可见的生成策略。此步骤用于提高用例质量，不是生成用例正文。

必须包含：
- 生成模式：标准/详细
- 预计条数与依据；详细模式通常为 80-200+，少于 80 条必须说明为什么范围确实较小
- 分批方式：写入端 / 读取端 / 联动 / 安全 / 缺陷回归
- must cover / should cover 范围
- history_bug / online_bug 覆盖策略和缺陷覆盖密度
- 关联模块覆盖范围
- 旧规则/旧用例的继承、覆盖、废弃或待确认结论
- 不覆盖项及原因

雷达辅助模式还必须包含：采用的雷达风险/测试点、被需求核心场景吸收的
测试点、仍需新增覆盖的测试点、排除或待确认项，以及与本地缺陷命中的
去重结果。不要为了雷达另建一套核心用例或映射状态机。

如果 Step 5 仍出现新的不确定项，必须回到 Step 4 问用户；否则可以进入 Step 6。

### Step 6: 用例生成

按 Step 5 策略生成用例。

生成前检查：
- `qa-knowledge/learned-patterns.yaml` 和 `.learnings/LEARNINGS.md` 存在时必读；不存在时按 `generator_kb_status: not_configured` 处理，不得伪造命中
- 必须消费 Step 4/5 的 must cover，不得只保留 `history_bug: true` 标记
- 预估 > 60 条时分批生成（写入端 → 读取端 → 联动 → 安全 → 缺陷回归）

缺陷驱动生成规则：
- 每条 `online_bug` must cover：至少生成 6-10 条（复现 R + 同场景变体 V + 同根因变体 C + 上下游联动 U + 保护性用例 G）。
- 每条 `history_bug` must cover：至少生成 3-6 条（复现 R + 同场景变体 V + 保护性用例 G，按风险补 C/U）。
- 生成的缺陷覆盖用例必须带字段：
  - `history_bug: true`
  - `bug_tier: online_bug/history_bug`
  - `history_bug_source: feishu/legacy_test_result_N/原始来源`
  - `source_bug_keys: [bug_key或来源文件#用例序号]`

上述固定缺陷密度规则只适用于本生成器独立命中的原始缺陷。雷达辅助
模式下，在同一个需求覆盖计划中直接吸收 `risks[].test_points`：同一业务
对象、条件、动作和可观察结果只保留一个场景；只有尚未覆盖的实质风险
才增加场景；不适用项说明原因，预期未确认项回到 Step 4。相同
`source_id` 只计算一次。雷达风险本身不决定固定用例数量，也不自动成为
P0/P1；优先级仍由业务影响、复发风险、漏测风险和确认范围共同决定。
雷达涉及的用例可按 `references/radar_integration.md` 添加可选追溯字段，
普通用例不得被要求添加。

覆盖策略：
- 按 FP 类型查 `references/coverage_strategies.md`
- 正常 + 异常 + 边界 + 安全（按页面实际组件触发）
- 标准模式可按规则合并；详细模式按值、状态、端、权限、版本、联动维度展开

**请求合理性与新旧数据兼容：**
- 根据 Step 4/5 已确认的适用检查，将具体要求写入用例前置、步骤和预期。业务预期仍未知时沿用现有澄清流程，不用“正常”代替确定预期。
- 请求检查涉及本次实际相关的前端页面、客户端或插件；数据检查保留受影响的代表性存量与新版本正常路径。
- 两项检查适用于标准和详细模式。模式简化不得用服务端校验或最终业务结果替代调用端请求观察；合并不得丢失有不同行为或预期的数据条件。
- 已有用例能完整承载检查时直接复用，不为新增分类重复生成，也不新增固定条数。
- 这些是固化的通用检查规则，不构成本次历史 Bug 或雷达命中，不因此触发缺陷扩写、增加历史来源元数据或计入雷达增益。

这里仅界定两项新增检查的执行方式，不将标准模式改成全面双端测试，也不重写现有通用去重规则。

输出格式：遵循 `references/output_format.md`。

生成时必须区分“一个核心验证目的”和“一个执行步骤”：原子用例可以包含多个有序动作。禁止用统一模板把所有 `steps` 写成 `1. <action>`；若步骤包含进入、输入、提交、刷新、再次操作等多个动作，必须拆成编号步骤。覆盖指纹的数据维度必须来自真实业务条件，不得使用标题、行号、随机值或哈希制造唯一性。

### Step 7: 自审与导出（强制执行，结果必须可见输出）

生成用例后必须执行自审。**自审结果必须在对话中显式输出**（覆盖率对照表 + 交叉检查 + 去重摘要），不可心里想了就跳过。

顺序：生成 → 自审输出 → 用户确认 → 导出 Excel

#### 7.0 用户确认后的快速导出路径（强制）

用户已经确认最终用例并只要求“确认导出”时，当前输入是已完成自审的最终
JSON/YAML，而不是新的需求分析任务。此时必须直接执行一次普通导出器：

```bash
python scripts/export_excel.py <最终JSON或YAML路径> output/<模块名>_v<版本>.xlsx --mode <standard|detailed>
```

- `export_excel.py` 直接读取 JSON 或 YAML，在同一进程完成质量校验、Excel
  写入、表头/行列数/冻结窗格/必填列复核。雷达辅助套件同时读取最终工件
  内的轻量 `radar_impact`，在同一次写盘中增加简洁的「雷达增益」Sheet；
  普通套件仍只生成 `testcases`。
- 不得重新读取需求、雷达、生成策略或自审材料；不得重跑雷达、生成或语义审查。
- 不得仅为导出把 JSON 转成 YAML。
- 不得先生成临时 Excel 再导入并二次导出，也不得默认执行全表渲染、分段重复
  渲染或创建额外工作簿。只有导出器失败，或用户明确要求定制工作簿样式时，
  才升级到针对性排查/表格编辑流程。
- 导出确认阶段只保留一个最终 `.xlsx`。目标是单条命令完成，工具执行通常应在
  10 秒内、用户可见总等待应在 60 秒内；超过时必须按实际单调用计时定位，
  不能把模型等待误报成 Excel 写盘耗时。
- 「雷达增益」只展示摘要、计数和一项风险一行的贡献说明，不复制完整步骤；
  不允许导出器为生成该 Sheet 回读雷达、状态或中间映射文件。

自审开始前必须先运行确定性质量门槛：

```bash
python scripts/validate_testcase_quality.py <用例JSON或YAML> --mode <standard|detailed>
```

步骤原子性、步骤与预期闭环、权限场景拆分等检查是普通与雷达辅助套件共用的
详细模式质量门槛，不是雷达专属行为。只有 `radar_impact` 的结构、计数和引用
检查由雷达字段条件触发；无雷达套件不需要也不得补这些字段。校验器须继续接受
既有无雷达工件中的历史 `type` 值，以保证旧 JSON/YAML 可以直接重新导出。

校验失败时不得声称自审通过或继续导出；修复后重新运行。该脚本不替代需求映射、状态矩阵和人工语义去重。

#### 7.1 覆盖完整性自审

- [ ] 当前需求适用的请求合理性与新旧数据兼容检查，是否已落入可执行的前置、步骤和预期？在现有自审结果中引用对应的最终用例编号或标题，核对关键断言；合并后再次核对。不能只写“请求正常”“兼容正常”。无相关影响时简短说明依据，无需展开全部方向的排除清单。

复用现有自审展示，相关检查可分组引用用例；不新增专项报告或独立覆盖矩阵。引用必须指向最终正文，不能仅有相关标题而缺少断言。

- [ ] **缺陷覆盖矩阵**（Step 4/5 有缺陷命中时必检）：
  - 输出矩阵：
    ```
    | bug_key/来源 | bug_tier | 模块 | 匹配分 | 覆盖用例ID | 状态 | 备注 |
    ```
  - `must_cover_bug_list` 每条都必须有覆盖用例。
  - 任一 `online_bug` 未覆盖 → 自审不通过，阻断交付。
  - 任一 `history_bug` must cover 未覆盖 → 回 Step 4 补充。
  - `should_cover_bug_list` 未覆盖时必须说明原因。

- [ ] **配置类需求**：
  - 写入端（配置页面）用例有了吗？
  - 读取端（配置生效场景）用例有了吗？
  - 读取端用例数量 ≥ 写入端的 50%？

- [ ] **关联模块联动覆盖**（Step 4/5 有输出时必检）：
  - 回头看 Step 4/5 的「缺失的关联点」清单
  - **逐条确认**：每个缺失关联点是否都已生成对应用例？
  - **输出改动影响 vs 用例密度对照表**（必须可见）：
    ```
    | 关联场景 | 改动级别 | 预估用例数 | 实际用例数 | 匹配? |
    ```
  - 🔴/🟡 级别场景偏少 → 回 Step 4 补充
  - ⚠️ 必须同时从关联规则角度补联动测试，不只是从 PRD 角度

- [ ] **功能操作类需求**：正向 + 异常 + 边界都有？

- [ ] **PRD 正向覆盖验证**：
  - 从 PRD 逐段提取功能点（含文案、站内信、注意事项中的可验证行为）
  - 建立「功能点 → 用例编号」正向覆盖矩阵
  - 无未覆盖的功能点（有 → 回 Step 4 补充）

#### 7.2 跨维度交叉自审

- [ ] **每组内维度变化**：
  - 识别本组"核心维度"和"其他维度"
  - 对每个其他维度问："换一个值，预期结果会不同吗？"
  - 会不同 → 本组内必须覆盖该维度的不同值
  - ⚠️ 不可全用最简单的值填充，分组是为了聚焦不是隔离

- [ ] **操作×对象状态矩阵**：
  - 不同操作 × 不同状态（新建/已上架/已过期等），覆盖了主要组合？
  - 编辑/删除场景有没有区分初始状态？
  - ⚠️ 思维模式：不是"功能能做什么"，而是"在什么状态下做，结果会不同"

- [ ] **不确定的业务逻辑**：
  - 对每个操作×状态组合判断：我知道预期结果吗？
  - 不知道 → 列入清单问用户，不能跳过

#### 7.3 去重自审

- [ ] **逐对比对**（不能只"感觉扫一眼"）：
  1. 列出所有用例的 [前置条件] + [预期结果]
  2. 逐对比对："这两条验证的是同一个业务规则吗？"
  3. 是 → 合并或删除

- [ ] **合并检查**：
  - 同一字段多个边界值 → 合并为一条
  - 同一字段多个异常值 → 合并为一条
  - 不同字段的测试 → 不合并

- [ ] **雷达辅助模式语义去重**：
  - 逐项确认高/中优先级雷达测试点已被某条最终用例覆盖，或有明确的排除/待确认原因。
  - 标题不同但业务对象、条件、动作和结果相同 → 合并并保留雷达来源。
  - 角色、状态、生效端、数据形态或预期不同 → 不得为了减少数量而合并。
  - 可见输出雷达风险数、测试点数、已覆盖数、排除数、待确认数；不得要求独立映射文件。

#### 7.4 场景粒度自审

- [ ] 每条用例只测一个核心点？多东西 → 拆分
- [ ] 多步骤是同一功能 → 保留；测不同功能 → 拆成多条

#### 7.5 输出格式自审

- [ ] `testcases` key（不是 `cases`），每条有 `scene` 字段
- [ ] `expected` 与 `steps` 对应关系正确
- [ ] 无抽象编码（"模式A/B"、"券A/B" → 全用中文直述）
- [ ] **增量模式额外检查**：同 scene 用例在 YAML 中连续？不允许跨组分散

#### 7.6 总量检查

- [ ] 用例总数合理？（< 15 太少，> 100 警惕）
- [ ] 各场景分布均匀？
- [ ] 优先级分布合理？（P0/P1 比例）

**⚠️ 自审不过 → 回到 Step 4/5/6 重新调整，直到所有项 ✅ 通过**

### Step 8: 反馈学习

用户修改用例时：
1. 执行修改
2. 分析类型：A规则缺失 / B覆盖遗漏 / C格式问题 / D理解偏差
3. 询问："这是通用规则吗？"
4. 是 → 存入知识库（rules/ 或 learned-patterns.yaml）
5. 否 → 记录到 `qa-knowledge/feedback-log.md`

### Step 9: 用例库归档

用户确认最终版本后：
1. 存入 `qa-knowledge/testcase-library/[模块名].yaml`
2. 更新 `index.yaml` 索引
3. 版本号 +1，记录 change_log
4. 如有 `execution_records` → 确认历史 bug 已内化 → 清理记录

**增量插入位置规则：** 新增用例必须插入到对应 scene 组内（找同 scene 最后一条之后插入），不能 append 到末尾。
```python
last_idx = max(i for i, c in enumerate(cases) if c.get('scene') == '目标scene名')
for i, new_case in enumerate(new_cases):
    cases.insert(last_idx + 1 + i, new_case)
```

## 输出格式速查

- **对话中**：TC-ID + FP + 优先级 + 前置条件 + 步骤 + 预期 + 类型
- **Excel 导出**：业务场景 + 用例标题 + 前置条件 + 步骤 + 预期 + 优先级（无 ID/关联/类型）
- **导出命令**：`python scripts/export_excel.py <JSON或YAML路径> <输出xlsx路径> --mode <standard|detailed>`；技能驱动的新生成任务必须传模式，质量校验失败时不得绕过导出器
- **文件命名**：`{模块名}_v{版本}.xlsx`（中文，不带"用例"，不用连字符）
- **完整格式规范**：见 `references/output_format.md`

## 基础规则

1. **步骤与预期对应** — 多步不同预期按编号对应；多步同预期写一条总结；单步直接写
2. **不要编造业务规则** — 不确定就问用户，宁多问不推测
3. **不要写死规则** — 页面有什么测什么，没有的不硬编
4. **用例要可执行** — 步骤包含具体测试数据
5. **追溯性** — 每条标注 FP 编号
6. **渐进式输出** — 先交叉分析与生成策略，再完整用例
7. **反馈即财富** — 每次修改都问是否存为规则
8. **加载 learned-patterns** — 生成前先读 `learned-patterns.yaml` 和 `.learnings/LEARNINGS.md`
9. **安全测试按组件触发** — 见上方安全测试段
10. **Excel 导出用 Python** — 使用 `scripts/export_excel.py`，不用 node xlsx

## Excel 入库时额外规则

从 Excel 入库用例时，必须处理合并单元格：
- 用 `ws.merged_cells.ranges` 构建映射（代码见 `references/self_review_checklist.md` 的合并单元格处理示例）
- 标题和前置条件**不做向上继承**，只有合并单元格才填充值
- 业务场景列（col0）可以向上继承
- 前置条件必须保留完整原文（"A或B"不能只留A）

## 知识库管理

目录：`qa-knowledge/`
- `rules/rule-NNN.yaml` — 业务规则
- `rule-index.yaml` — 规则索引
- `learned-patterns.yaml` — 从反馈提炼的模式
