# 用例输出格式

## 输出场景区分

### 对话中展示（完整格式）
用于对话中给用户即时查看，包含所有字段：
- TC-ID、关联 FP、优先级、前置条件、测试步骤、预期结果、测试类型

### 文件导出（精简格式）
用于输出 Excel / 文档等，只保留核心字段：
- 业务场景、优先级、用例标题、前置条件、测试步骤、预期结果
- **不要** ID、关联、测试类型

## 对话展示格式：Markdown 结构化

### 整体结构

```markdown
# [需求名称] 测试用例

## 需求追溯
- 需求来源: [文档名/描述]
- 分析日期: YYYY-MM-DD
- 命中规则: [规则名] 或 无

## 需求分析摘要
### 功能点
- FP1: ...
- FP2: ...

### 约束条件
- C1: ...

---

## 场景一: [业务场景名称]

### TC-001: [用例标题]
- **关联**: FP1
- **优先级**: P0/P1/P2
- **前置条件**: [条件描述]
- **测试步骤**:
  1. [步骤1]
  2. [步骤2]
  3. [步骤3]
- **预期结果**:
  - [结果1]
  - [结果2]
- **测试类型**: 正向/异常/边界/权限/集成

### TC-002: [用例标题]
...

---

## 场景二: [业务场景名称]
...

---

## 覆盖统计
| 维度 | 用例数 | 覆盖 FP |
|------|-------|---------|
| 正向 | N | FP1,FP2,... |
| 异常 | N | FP1,... |
| 边界 | N | FP2,... |
| 权限 | N | ... |
| 集成 | N | ... |
| 合计 | N | |
```

## 用例编写规范

### 用例标题
- 格式: `[操作主体] + [操作] + [条件/场景] + [预期]`
- 好: "管理员删除已完成订单时提示确认"
- 差: "测试删除功能"

### 测试步骤
- 每步一个动作，不要合并多个操作
- 明确指出操作对象（哪个按钮、哪个输入框）
- 包含测试数据（具体的值，不要用"某个值"）

### 预期结果
- 具体、可验证（不要用"正常显示"）
- 包含数据验证（字段值、状态变化）
- 包含 UI 反馈（提示信息、页面跳转）
- **与步骤的对应关系**：
  - 多个步骤且预期结果不同 → 按编号一一对应（1. 步骤A → 1. 预期A）
  - 多个步骤但预期结果相同 → 写一条总结即可，不要强行逐条重复
  - 单个步骤 → 直接写预期，不需要编号

### 优先级定义
- **P0**: 核心功能，阻塞发布（必须通过）
- **P1**: 重要功能，影响主流程（应该通过）
- **P2**: 次要功能，边界/兼容场景（建议通过）

## Excel 导出

### 导出脚本
使用 `scripts/export_excel.py`，支持命令行调用或在代码中 import：
```bash
python scripts/export_excel.py <yaml路径> <输出xlsx路径> --mode standard|detailed
```

生成流程必须传入实际模式。传入 `--mode detailed` 时，导出器会先执行
步骤原子性和步骤-预期闭环校验；校验失败不会写出 Excel。旧调用仍可省略
`--mode` 以保持兼容，但技能驱动的新生成任务不得省略。

### Excel 样式规范
- **表头**：蓝底白字（#4472C4），微软雅黑 11号加粗，居中
- **数据行**：微软雅黑 10号，自动换行，顶部对齐
- **条件高亮**：
  - P0 用例行：浅红背景（#FCE4EC）
  - 安全测试用例行：浅橙背景（#FFF3E0）
- **边框**：全部细边框
- **冻结首行**：方便滚动时看表头
- **列宽**：业务场景18 / 优先级8 / 标题30 / 前置条件30 / 步骤45 / 预期45

### 输出路径
统一输出到 `output/` 目录，不放 workspace 根目录。

### 文件命名规范
统一使用中文模块名 + 下划线 + 版本号：`{模块名}_v{版本}.xlsx`
- 示例：`Banner管理_v2.xlsx`、`支持平台管理_v4.xlsx`、`设备购买_v2.xlsx`
- 不要用英文名、不要带"用例"二字、不要用连字符

## YAML 存储格式（用例库统一规范）

所有模块的用例 YAML 文件必须使用统一的字段结构：

```yaml
module: "模块名"
description: "模块描述"
version: 1
updated_at: "YYYY-MM-DD"
requirement_summary: |
  需求概述...

change_log:
  - version: 1
    date: "YYYY-MM-DD"
    change: "变更说明"

testcases:                    # ← 统一用 testcases，不用 cases
  - module_group: "功能模块名" # ← 可选，多模块需求时必填，对应 Excel「功能模块」列
    scene: "业务场景名"       # ← 必填！对应 Excel 的"业务场景"列
    priority: P0              # P0/P1/P2
    title: "用例标题"
    precondition: "前置条件"
    steps: |
      1. 步骤1
      2. 步骤2
    expected: "预期结果"
    type: "正向"              # 正向/异常/边界/权限/集成/安全/功能
    fp: [FP1, FP2]            # 关联功能点
```

新生成工件必须使用上述中文 `type`。为保证历史普通用例可直接重新导出，
不含任何雷达元数据的既有工件可继续使用已知旧值 `api_behavior`、`workflow`、
`data_record`、`constraint`、`config`；这是导入兼容，不是新生成格式。

**关键约束：**
- `testcases`：统一用这个 key，不用 `cases`
- `module_group`：**可选**，当需求涉及多个功能模块时必填（如来自多个 Sheet 的用例合并入一个文件），对应 Excel 导出的「功能模块」列
- `scene`：**必填**，对应 Excel 导出的"业务场景"列，按业务场景分组命名
- `priority`：P0/P1/P2，不带引号也行
- `steps` 和 `expected`：用 `|` 多行格式，保持可读性
- 对话中额外展示 TC-ID 和关联 FP，但 YAML 中 `fp` 字段保留追溯用

### 雷达辅助模式的可选追溯字段

仅当当前需求存在合法 `radar_result`，且最终用例实际吸收了某项雷达测试点
时，可以附加 `radar_risk_ids`、`radar_source_ids`、
`radar_evidence_types`。这些字段不是普通模式必填项，不得批量添加到无雷达
用例，也不新增 Excel 列。

雷达辅助模式的最终 JSON/YAML 还应包含一个顶层 `radar_impact`：只保留
摘要、覆盖计数，以及每项风险如何增强或新增用例的简短说明和对应 TC-ID。
导出器在同一个工作簿中增加「雷达增益」Sheet；普通无雷达套件不包含该对象，
仍只导出 `testcases` Sheet。

**导出映射：**
| YAML 字段 | Excel 列 | 说明 |
|-----------|---------|------|
| module_group | 功能模块 | 可选，有则显示、无则不显示该列 |
| scene | 业务场景 | 必填 |
| title | 用例标题 | 必填 |
| precondition | 前置条件 | |
| steps | 测试步骤 | |
| expected | 预期结果 | |
| priority | 优先级 | 放最后一列 |

## 按业务场景组织

用例按业务场景（而非技术模块）组织：

```
❌ 错误: 按技术分
├── 前端验证用例
├── 接口测试用例
└── 数据库验证用例

✅ 正确: 按业务场景分
├── 场景一: 用户正常下单
├── 场景二: 用户使用优惠券下单
├── 场景三: 库存不足时下单
└── 场景四: 管理员取消订单
```
