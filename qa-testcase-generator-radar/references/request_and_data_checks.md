# 请求合理性与新旧数据兼容固化规则

历史场景只用来提炼检查方法，不将特定工单的期望、根因或临时数值固化为所有业务的规则。固化的是“需要核对什么”，具体业务结果以当前需求、有效规则及确认信息为准。

## 请求合理性

适用于本次涉及的前端页面、客户端和插件，不机械将所有用例复制成三端。

| 检查目的 | 相关场景及正文要求 |
|---|---|
| 该发起时发起 | 有效提交、切回刷新、页面重建、进程再次唤起、插件入口、批量后续调度：满足条件时必要调用按设计发生；有效缓存或本地处理不误判为漏发 |
| 不该发起时不发起 | 本地校验失败、未确认/取消、无权限、上游失败、开关关闭、启动模式/共享授权限制：按当前规则核对禁止条件下的目标业务调用是否被阻止；必要鉴权、远端校验和清理请求单独判断 |
| 没有不合理重复 | 重复点击、快速输入、切页、重复挂载/监听/注入、多端桥接、循环状态、失败恢复：按同一业务操作核对实际尝试及停止规则，不以同 URL 直接判重复 |
| 没有无效请求 | 公司/账号切换、路由缺失、错误参数、隐藏字段、外部唤起、线路变化、批量超时和旧任务：请求对象、身份、目标地址、参数语义及生命周期有效 |

观察与计数约束：

- 识别实际网络出口；宿主页面 Network 不一定覆盖客户端或插件后台。页面→客户端→服务端的正常转发不能跨层相加当作重复。
- 区分首次发送、自动重试和用户重提；轮询、心跳、预取、分片及批量分段按当前规则判断，不统一要求“一次操作只能一条请求”。
- 区分关闭后新发、关闭前已发、迟到响应和服务端推送；取消本地等待不证明服务端未处理。
- 按钮无反应、重复日志、错误响应或慢响应不能单独证明请求根因；服务端只产生一条记录也不能证明调用端只发送一次。
- 用例写清目标业务请求、触发条件、观察方式及发送/禁止/次数或控制规则。未知 URL 不编造；历史防抖、超时和批量建议值不作为当前通用阈值。

## 新旧数据兼容

先检查受影响的基本路径，再根据实际差异展开：

- 本次改变既有数据的读取、解析、展示、保存或消费逻辑时，即使结构未变，也应验证代表性历史记录，并覆盖新版本正常创建与使用路径。
- 按实际生产入口、字段/取值、业务规则、关联及迁移/修复状态识别差异。创建时间仅作辅助：历史记录可能已迁移，新版本导入也可能保留旧格式或缺配置。
- 特殊差异决定额外展开范围，不是存量基本回归的前提；全新对象确无存量时不伪造历史数据。

| 当前变更线索 | 固化检查要点 |
|---|---|
| 新校验、状态或默认值 | 旧合法值的读取、原样保存、修改其他字段；区分缺失、空、零和关闭；保留/转换/拒绝依据当前规则 |
| 创建入口、同步或升级变化 | 手动、导入、接口等实际入口产生的数据；字段、子配置和关联完整性；跨版本的值保留或转换、本地配置继承是否符合当前规则 |
| 保存逻辑变化 | 保存前后对照；核对未显式修改字段的保留、联动重置或转换是否符合当前规则；授权关系应按规则保持或联动调整，避免非预期扩大或缩减 |
| 作用域、参数或绑定变化 | 企业/账号/成员范围、新旧参数共存、旧关系处理与有效关系选择；核对解绑对关联记录和主体数据的保留、失效或删除行为是否符合当前规则 |
| 导入导出、新类型或消费端变化 | 实际支持的格式、语言、模板和生产/消费组合；数据产生后能否展示、继续操作或撤销 |
| 异常写入修复 | 正常存量、异常存量、新版本正常数据分别判断；代码修复不代表历史异常已补修 |
| 模式、开关、快照或排序变化 | 历史可见性、配置存在与启用状态、有效快照、稳定排序及分页/全选；不能仅根据界面不可见推断物理删除，按当前规则核对数据保留及可见范围 |

样本与正文要求：

- 前置写可识别的数据特征及取得/构造方法，步骤执行受影响的读写，预期写明确的值、状态、关系或业务结果。不能只把创建日期改早就当作旧结构。
- 不强制每次准备全部数据类型；迁移重跑、回滚、精度单位、归档或并发新旧写入，仅在本次存在对应机制时展开。
- 具体样本 ID、账号、日志路径等属于准备信息；不要仅因这些信息缺失就新增业务澄清。保留还是转换、是否允许操作等会改变预期的问题，沿用现有流程确认。
