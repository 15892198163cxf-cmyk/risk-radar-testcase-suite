# 自审与优化清单（Step 7，强制执行）

## 7.0 合并单元格识别 + 前置条件继承自审（Excel 入库时强制）

### 7.0a 合并单元格识别（强制前置步骤，不可跳过）

Excel 入库时，**所有字段**（业务场景、用例标题、前置条件、测试步骤、预期结果）都必须通过合并单元格感知方式读取：

**强制规则：**
1. **使用 `ws.merged_cells.ranges` 构建合并单元格映射**：扫描所有合并区域，对于每个被合并的 (row, col)，映射到合并区域左上角的值
2. **读取每个单元格时**：先读原始值，如果是 None，再查合并映射拿到合并区域的值
3. **不可用「向上继承」替代合并单元格识别**：标题（col2）和前置条件（col3）**不做向上继承**——只有合并单元格才填充值，非合并且原表空就是空
4. **业务场景（col0）例外**：可以向上继承（因为 Excel 中业务场景列通常用合并单元格表示分组，语义上等同于继承）

**代码模式（Python + openpyxl）：**
```python
def build_merged_map(ws):
    merged_map = {}
    for m in ws.merged_cells.ranges:
        val = ws.cell(row=m.min_row, column=m.min_col).value
        for row in range(m.min_row, m.max_row + 1):
            for col in range(m.min_col, m.max_col + 1):
                merged_map[(row, col)] = val
    return merged_map

def get_cell(ws, merged_map, row, col):
    val = ws.cell(row=row, column=col).value
    if val is not None: return val
    return merged_map.get((row, col), None)
```

**典型错误（已踩坑）：**
- 原表「传输功能」合并跨 25 行，openpyxl 默认只有第 1 行有值，其余 24 行读出 None
- 不用合并映射 → 24 条用例标题变成空 → 丢失了「这些行都属于传输功能」的语义
- 同理：前置条件（如「MAC」「win」「远程码有效」等）也有合并单元格

### 7.0b 前置条件完整性自审

从 Excel 入库时，原表往往有**合并单元格 / 层级继承**结构：父行的前置条件适用于下面所有子行。

**自审步骤：**
1. **已通过 7.0a 合并单元格识别**：确认前置条件字段已正确读取合并区域的值
2. **逐条核对**：拆条后，每条用例的前置条件必须包含父行的**完整原文**（不能缩写、不能省略「或XX」等并列条件）
3. **原文对比验证**：把拆条后的前置条件和原表的 col3 原文做**逐字对比**，发现缺字/少条件立即补全
4. **特别注意**：
   - 「A或B」不能简写成只有A
   - 表名引用（如 `crm.t_ik_customer_operation`）不能丢
   - 多条件用换行分隔时，每个条件都要保留

**典型错误（已踩坑）：**
- 原表写「企业未配置业务负责人**或者业务负责人被删除**(crm.t_ik_customer_operation)」
- 拆条后只写了「企业未配置业务负责人」→ 丢掉了「或者业务负责人被删除」这个并列条件
- **根因**：拆条时只抓了主干，没有完整复制父行的前置条件原文

## 7.2 跨维度交叉自审

对每个用例分组，检查非核心维度是否有变化：

- [ ] **每组内维度变化**:
  - 该分组的核心维度充分覆盖了吗？
  - 其他维度（设备类型/折扣/状态/权限等）有变化吗，还是全部用同一个值？
  - 如果换个维度值，预期结果会变吗？如果会 → 必须在本组内体现

- [ ] **操作×对象状态矩阵**:
  - 不同操作（添加/编辑/删除）× 不同对象状态（新建/已上架/已过期），覆盖了主要组合吗？
  - 特别是编辑/删除场景，有没有区分对象的初始状态？

## 7.3 去重自审

- [ ] **逐对比对**（不能只是"感觉扫一眼"）:
  1. 列出所有用例的 [前置条件] + [预期结果]
  2. 逐对比对，问："这两条验证的是同一个业务规则吗？"
  3. 如果是 → 合并或删除重复项

- [ ] **同字段同类测试合并检查**:
  - 同一字段的多个边界值 → 合并为一条
  - 同一字段的多个异常值 → 合并为一条
  - 不同字段的测试 → 不合并

## 7.4 场景粒度自审

- [ ] **单一职责原则**:
  - 每条用例是否只测一个核心点？
  - 是否存在"同时测多个东西"的用例？（如果有 → 拆分）

- [ ] **多步骤用例的合理性**:
  - 多个步骤是为了同一个功能吗？（是 → 保留多步）
  - 还是在测不同的功能？（是 → 拆成多条）

- [ ] **原子性与步骤数量没有混淆**:
  - 一条用例可以有多个顺序动作，但只能有一个核心验证目的。
  - 单步中是否出现“输入并保存”“删除后刷新”“打开并调用接口”等动作压缩？有则拆成编号步骤。
  - 预期中出现的接口/UI动作是否都能在步骤中找到对应操作？
  - 详细模式的前端权限显隐与后端接口鉴权是否已拆成不同用例？

## 7.5 输出格式自审

## 7.6 最终检查

生成的用例总数 vs 预期：
- [ ] 用例总数合理吗？（太少 < 15条、太多 > 100条 需要警惕）
- [ ] 各场景分布均匀吗？（有没有某个场景特别少或特别多？）
- [ ] 优先级分布合理吗？（P0/P1 的比例是否合理？）
- [ ] 已运行 `scripts/validate_testcase_quality.py` 且结果为 `VALID`？
- [ ] 详细模式不少于20条时，是否检查了单步骤占比和单步多动作数量？
- [ ] 语义指纹中的数据条件是否来自真实业务数据，而不是标题、行号或随机值？
