# 用例生成详细规则

## 11. 每组用例跨维度交叉检查（强制步骤，不可跳过）
每组用例生成后：
- **Step A**: 识别本组的"核心维度"和"其他维度"（如：本组核心=优惠券限制，其他=设备类型、折扣种类、套餐状态）
- **Step B**: 对每个"其他维度"问：**"换一个值，预期结果会不同吗？"**
- **Step C**: 如果答案是"会不同" → 本组内必须覆盖该维度的不同值，不能全用同一种
- **Step D**: 输出检查结果（如："本组8条全是非专用设备 → 需要混合专用设备"）
- ⚠️ 不可以全用最简单的值填充其他维度（比如全用非专用设备因为计算最简单）
- ⚠️ 分组是为了聚焦，不是为了隔离。每组内部也要有其他维度的变化

## 12. 操作×对象状态交叉检查（强制步骤，不可跳过）
生成前和生成后：
- **生成前 Step A**: 列出被测对象的所有状态维度（如：展示时间类型、上下架状态、发布状态、设备类型等）
- **生成前 Step B**: 形成「操作×状态」矩阵，标记哪些组合下行为会不同
- **生成后 Step C**: 检查每个操作场景是否覆盖了不同状态组合，而不是全用默认/最常见状态
- ⚠️ 不要把"状态相关的场景"单独分一组后，就认为其他组不需要考虑该状态
- ⚠️ 思维模式：不是"这个功能能做什么"，而是"这个功能在什么状态下做，结果会不同"

## 13. 不确定的业务逻辑必须问，不能跳过
Step 4 交叉分析与澄清门控阶段：
- 列出被测对象的状态矩阵后，对每个「操作×状态」组合判断：**我知道预期结果吗？**
- 如果不知道 → 加入「澄清问题」或「不确定业务逻辑清单」，在 Step 4 输出时一并列给用户确认
- ⚠️ "不确定"≠"不重要"，不能因为不知道答案就跳过不覆盖
- ⚠️ 宁可多问几个问题，也不要自己推测或直接无视

## 14. YAML 格式必须统一
所有模块用例 YAML 必须遵循 `references/output_format.md` 中的「YAML 存储格式」规范：
- key 统一用 `testcases`（不用 `cases`）
- 每条用例必须有 `scene` 字段（对应 Excel "业务场景"列）
- 字段顺序：scene → priority → title → precondition → steps → expected → type → fp

## 15. 配置类需求必须追踪下游生效场景
任何"在X页面增加/修改Y配置"的需求：
- Step 4 必须判断并在必要时澄清：**"这个配置在哪里被消费/生效？"**
- 写入端（配置页面UI）和读取端（生效场景）都要测
- 配置页面的用例 ≠ 完整覆盖，下游业务效果验证才是核心
- ⚠️ 不要被需求描述的"页面范围"限制思维，要追踪数据流

## 16. PRD 功能点正向覆盖（强制步骤，不可跳过）
生成用例后、交付前：
- **Step A**: 从 PRD/需求文档中逐段提取所有可验证的功能点，编号列出（包括独立功能模块、提示语文案、站内信内容、注意事项、规则说明中的可验证行为）
- **Step B**: 建立「PRD 功能点 → 用例编号」正向覆盖矩阵
- **Step C**: 标记未被任何用例覆盖的功能点，补充对应用例
- ⚠️ 方向必须是 **PRD → 用例**（正向），不能只做 **用例 → PRD**（反向验证只能证明"已有的没编错"，不能证明"没遗漏"）
- ⚠️ 藏在文案/站内信/注意事项里的可验证行为也是功能点

## 17. 关联分析结果必须在 Step 5/6 被消费
如果 Step 4/5 输出了「缺失的关联点」：
- Step 6 生成时必须**同时覆盖两个来源**：需求文档遗漏 + 关联模块联动
- Step 7 自审时必须**逐条对照** Step 4/5 的缺失清单
- ⚠️ 不要做了分析又「忘了」——分析和生成之间不能断裂

## 18. 用例密度跟着改动点走
不按关联条数机械分配，按改动影响分级：
- 🔴 新增/重写 → 细测（校验、边界、交叉）
- 🟡 逻辑变了 → 中测（核心路径 + 关键边界）
- 🟢 数据源变了没改逻辑 → 粗测（跑通即可）
- ⚪ 完全没动 → 不测或冒烟
- Step 4/5 输出改动影响分级表，Step 7 对照验证密度是否匹配

## 19. 预估 > 60 条时分批生成
避免文件截断丢失后半段用例：
- 分3-4批：写入端 → 读取端 → 联动 → 安全
- 每批独立 YAML，最后 Python 脚本合并
- 合并后验证：总条数 = 各 part 之和

## 20. 关联分析必须逐scene映射
Step 3 知识库命中读取关联模块时：
- 列出每个关联模块的 scene 列表
- 逐个标记：✅需要覆盖 / ❌不需要（说明理由）/ ❓不确定（问用户）
- ⚠️ 不能只统计 scene 数字就完事，必须逐条映射

## 21. 合并用例看规则不看字段
去重合并时：
- 同一规则的不同输入值 → 可合并（名称中文/英文/混合）
- 不同规则/不同测试维度 → 不合并（正常输入 vs 边界值 vs 特殊字符 vs 格式校验）
- 判断标准："这两条验证的是同一条业务规则吗？" 是→合并 否→保留

## 22. 自审结果必须可见输出
生成完不能直接交付：
- 对话中输出覆盖率对照表 + 交叉检查 + 去重摘要
- 顺序：生成 → 自审输出 → 用户确认 → 导出 Excel
- ⚠️ 心里想了但没输出 = 没做

## 23. 生成后先运行机械质量校验

在自审和导出前运行：

```bash
python scripts/validate_testcase_quality.py <用例JSON或YAML> --mode <standard|detailed>
```

出现以下任一错误时禁止导出：

- 详细模式用例集被机械压成单步骤；
- 一个编号步骤包含多个可执行动作；
- 预期声明接口结果，但步骤没有接口调用；
- 同一详细用例混合前端权限显隐与后端接口鉴权；
- 用例类型不在规定枚举内。

机器校验通过只代表这些确定性问题未出现，不能替代需求正向映射、状态矩阵和人工语义去重。

## 24. 语义去重必须来自业务条件

- 用业务对象、入口、角色、状态、数据、动作和可观察结果判断是否重复。
- 禁止用用例标题、行号、随机数或标题哈希制造差异。
- 标题不同不能作为“不重复”的证据；业务条件不同也不能为了缩短数量强行合并。
