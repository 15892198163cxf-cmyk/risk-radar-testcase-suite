# Risk Radar Testcase Workflow

风险雷达到测试用例的组合工作流。它先为当前需求执行一次适用的测前风险雷达，再把同一份结构化雷达结果交给专用的 `qa-testcase-generator-radar`，并由 `qa-testcase-reviewer-radar` 完成独立评审。普通生成器和评审器不参与该链路。

对于紫鸟需求，默认使用 `ziniao-landmine-map` 作为雷达提供方。

## 适用场景

- 希望先查历史线上 Bug 和测试经验，再生成完整测试用例。
- 需要雷达风险真正落到最终用例，而不是只得到一份风险说明。
- 需要详细模式用例、质量校验和 Excel 导出。
- 需要说明哪些原有需求用例被雷达复核强化、哪些是雷达新增用例。
- 希望避免雷达和生成器分别分析两次、问题重复询问或用例无意义膨胀。

## 不适用场景

- 只需要查看历史风险和测试提醒，不生成完整用例时，使用 `ziniao-landmine-map`。
- 明确不使用雷达，只按需求生成普通用例时，使用 `qa-testcase-generator`。
- 已经有完整用例，只需要二次评审时，使用 `qa-testcase-reviewer`。
- 需要直接执行接口测试时，使用 `api-security-tester`。

## 常见触发话术

- 使用 `$risk-radar-testcase-workflow` 分析这份需求并生成测试用例。
- 先跑风险雷达，再按详细模式生成用例。
- 结合紫鸟历史线上 Bug 帮我补强这份 PRD 的测试用例。
- 用雷达增强模式生成用例，最后导出 Excel。
- 雷达和普通需求覆盖合并去重后再出用例。

## 输入材料

- PRD、飞书需求、Markdown、PDF、图片或粘贴的需求文本。
- 用例模式：标准模式或详细模式。
- 可选：验收标准、原型、接口说明、明确的不覆盖范围。
- 可选：新功能/旧功能改动、目标端、角色、状态、版本和数据范围。

只选择模式不代表可以跳过需求分析和澄清。工作流仍遵循雷达专用生成器的分析、澄清、策略确认、自审和导出门槛。

## 工作流程

```text
同一份需求材料
  -> ziniao-landmine-map 执行一次雷达分析
  -> 生成并校验 canonical radar_result
  -> qa-testcase-generator-radar 解析需求并合并雷达测试点
  -> 统一澄清问题和生成策略
  -> 生成完整测试用例
  -> 校验雷达风险是否真正被用例消费
  -> qa-testcase-reviewer-radar 独立评审并修复高/严重问题
  -> 用户确认
  -> 一次导出最终 Excel
```

工作流不会先生成一套普通用例，再额外生成一套雷达用例。相同业务对象、条件、动作和结果会合并；只有仍未覆盖的实质风险才新增用例，即“雷达增强，不雷达膨胀”。

## 输出结果

- 需求分析、知识库命中摘要和雷达风险摘要。
- 合并去重后的待确认问题及建议口径。
- 标准模式或详细模式的完整测试用例。
- 用例质量校验和自审结论。
- 雷达消费统计：收到、覆盖、排除、待确认的风险和测试点。
- 最终 Excel：
  - `testcases`：完整测试用例；
  - `雷达增益`：雷达复核强化、雷达新增用例和排除/待确认说明。

## 使用示例

### 详细模式并导出 Excel

```text
使用 $risk-radar-testcase-workflow 分析这份 PRD。
按详细模式执行，先完成需求识别和澄清，确认后生成测试用例，最后导出 Excel。
```

### 指定紫鸟新功能

```text
使用 $risk-radar-testcase-workflow 分析运维后台新增抖店实物订单发券功能。
这是新功能，请先执行 ziniao-landmine-map，再把雷达结果合并进详细用例，不要重复生成场景。
```

### 不需要雷达

如果本次只想验证原始需求，不需要历史风险增强，应直接说：

```text
使用 $qa-testcase-generator 按详细模式分析这份需求，不使用风险雷达。
```

## 与单独调用的区别

| 调用方式 | 结果 |
| --- | --- |
| `ziniao-landmine-map` | 只输出风险、证据、测试点和边界，不生成完整用例。 |
| `qa-testcase-generator` | 不使用雷达，按原流程生成普通测试用例。 |
| `risk-radar-testcase-workflow` | 执行雷达，并通过隔离的雷达生成器和评审器产出一套最终用例。 |

## 关键使用边界

- 雷达和生成器必须使用同一份需求材料。
- 一次任务只执行一次雷达，预览和生成器交接来自同一个 `radar_result`。
- 雷达测试点是高价值分析输入，不自动视为当前需求规则或固定优先级。
- 雷达问题和生成器问题统一去重，但未经用户确认的问题仍然是待确认项。
- 工作流不修改雷达证据库，也不默认写回飞书或外部系统。
- 没有适用雷达提供方时，回退到普通生成器，并明确说明本次未使用雷达。
- 雷达增强链路只能调用 `qa-testcase-generator-radar` 和 `qa-testcase-reviewer-radar`；无适用雷达时退出该链路，再按普通流程处理。

## 依赖 Skill

- `ziniao-landmine-map`：紫鸟需求的风险雷达提供方。
- `qa-testcase-generator-radar`：工作流专用的需求分析、澄清、用例生成、自审和 Excel 导出。
- `qa-testcase-reviewer-radar`：工作流专用的独立二次评审和雷达追溯检查。
- `qa-testcase-generator` / `qa-testcase-reviewer`：普通无雷达流程，工作流不得修改或调用。

## 维护验证

在工作流目录执行：

```powershell
py -m unittest discover -s scripts -p "test_*.py"
```

主要校验：

- `radar_result` 结构和同次运行一致性；
- 独立运行结果的回归差异；
- 最终用例对雷达风险和测试点的消费统计；
- 用例 ID、强化/新增分类和 Excel 雷达增益数据的一致性。
- 普通生成器、普通评审器与 `origin/master` 的零差异，以及两个雷达专用 Skill 的显式调用策略。
